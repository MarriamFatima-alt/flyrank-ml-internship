Refresh or wait: ranking content before it bleeds traffic

A field report on scoring 30,000 pages for editorial review — and on the difference between a validation split that flatters a model and one that tells the truth.

Abstract Editorial teams reviewing hundreds of pages have no reliable way to know which ones need attention first. Using 30,000 anonymized FlyRank content records across 32 clients, I compared a transparent rule-based baseline against logistic regression, a decision tree, and a random forest, validated on a client-holdout split so no client's pages appear in both training and test. The random forest placed a genuinely declining page in its top 50 recommendations 74% of the time — a 3.1× lift over the 24% baseline rule, and well above the 54% base rate. The same model looked far stronger, 90% precision@50, under a naive random split that let 31 of 32 clients leak between train and test; that gap is the paper's central finding. The output is a ranked review queue with plain-language reason codes, not an automated publishing decision.

01

The problem this supports

A content team with a few thousand live pages cannot manually re-check each one every month. Something has to decide the order of the review queue.

Unit of analysis: one content page (content_id). Decision supported: which pages an editor opens for review this week, out of far more candidates than there is time to check. Output: a rank, a confidence tier, a suggested action, and the reasons behind it — not a publish/unpublish decision.

Cost of getting the order wrong: a missed decliner keeps losing impressions silently until someone happens to notice; a false alarm costs an editor a few minutes checking a page that turns out to be fine. Because the second mistake is cheap and the first is a slow leak, the review queue is designed to rank generously rather than filter aggressively — see Limitations for what that trade-off means in practice.

A hand-written rule can already flag some of this (see the baseline below). The question this capstone asks is how much a model, honestly validated, actually adds over that rule — and whether the improvement survives a validation split that doesn't cheat.

02

Data

The FlyRank ML-internship warehouse slice, anonymized before it reaches interns.

  • 30,000 content rows across 32 pseudonymous clients (client_id used only for grouping, never as a feature).
  • 90-day trailing search performance (impressions, clicks, sessions, position, CTR, scroll rate) plus on-page signals (word count, content age, days since last update) and 30-day trend windows.
  • Excluded on purpose: titles, URLs, domains, client names, keywords, and raw exports — nothing in this report or the underlying repo can identify a client or page.
  • Label — is_declining_label: 1 when trend_direction == "down" (last-30-day impressions more than 20% below the prior 30 days), else 0. 16,262 of 30,000 rows (54.2%) are labeled declining — close enough to balanced that accuracy alone would be a weak metric, which is why this report leads with precision@50 against that base rate.
Why trend_direction and trend_pct are never features Both columns define the label itself. Feeding either into the model would let it read the answer off the input. Excluded from the feature set at the pipeline level, not just at review time — see scripts/ml_utils.py.
03

Methodology

Baseline — a rule anyone can read

Before any model, a deterministic scoring rule flags pages on stated conditions: stale + still visible, declining with real demand behind it, thin content still getting impressions, a page-one position that's aging, low CTR at high visibility, low engagement at real traffic. Any editor can check the rule against a page by hand — that transparency is the point of having a baseline at all, and every model below has to beat it on the same split and metric to earn its place.

Models compared

Logistic regression, a decision tree, and a random forest, all from scikit-learn, all trained on the same feature matrix. Categorical fields (competition level, content type, main intent, age/freshness/word-count/impression/position tiers) one-hot encoded; numeric fields include log-scaled traffic volumes, CTR, average position, engagement and scroll rate, content age, and days since last update — 30-plus features total, none of them titles, URLs, or label-derived.

Split design — client holdout, not random rows

Pages from the same client share a lot of structure (template, publishing cadence, niche). A random row-level split lets a model see one page from a client during training and a different page from the same client during testing — which quietly leaks client identity into the score. Every number in the Results section below, unless labeled otherwise, comes from a client-holdout split: entire clients are held out of training and scored only at test time.

Leakage audit

Before finalizing features, I checked whether the 90-day traffic totals used as features were quietly re-deriving the label's own 60-day window. They were closely related: impressions_90d correlates 0.98 with the sum of the label's two 30-day windows, and that 60-day sum covers on average 56.2% of the 90-day total. The label-defining columns (trend_direction, trend_pct, and the raw 30-day windows) were kept out of the model's feature list entirely — the model only sees the 90-day aggregate, not the windows that built the label.

Why the split matters more than the model

Run the identical random forest under a naive random row split — the split most tutorials use by default — and the numbers look considerably better. They're wrong.

Careful language Observed: on a client-holdout test set, the model's top-50 ranked pages contained a declining page 74% of the time, against a 54.2% base rate. This is decision-support for review prioritization, not a causal or guaranteed prediction for any single page — and it says nothing about Google's ranking algorithm itself.

The top four features are almost entirely about how consistently and visibly a page has been showing up — not about content quality signals like word count, which ranks well down the list. Read plainly: the model has mostly learned to distrust pages whose visibility has gone patchy, more than it has learned anything about what makes content good.

05

Limitations & honest framing

  • Observational, not causal. The model finds pages that look like past decliners. It does not explain why a page is declining, and refreshing a flagged page is not guaranteed to reverse the trend.
  • 32 clients is a small holdout universe. Client-level validation is the honest choice, but it also means the test set is coarse — a handful of unusual clients can move the headline number more than they would in a larger sample.
  • 60% of rows carry low confidence. 15,000 of 30,000 queue rows are tagged low confidence by the pipeline's own criteria; those need more scrutiny before acting, not less.
  • One bucket is too small to generalize from. Only 82 rows fall into expand_and_refresh — treat that action as a lead worth a manual look, not a validated pattern.
  • Anonymized starter slice, not the full warehouse. Numbers here are computed on the ~30k-row public sample; they will shift (not necessarily worsen) on the full internship dataset.
  • No client or page identifiers appear anywhere in this report, consistent with the internship's data-safety rules.

Intended use

This queue is a reviewer aid, not an autopublish trigger. The recommended workflow: an editor opens high-confidence rows first, checks the page against the listed reason codes, and only then decides whether to refresh, expand, or leave it. Low-confidence rows are a hint to look, not an instruction to act.

Monitoring / retrain triggers

Treat this run as the baseline snapshot to watch: precision@50 of 0.740, base rate of 0.542, and the action mix above. If a future re-run drifts more than a few points on any of these against a fresh honest split, that's the signal to re-check features and retrain before trusting the queue again.

Reproducibility

Every number in this report comes from a fresh run of the pipeline in this repo, on the bundled anonymized sample:

From a clean clone git clone https://github.com/MarriamFatima-alt/flyrank-ml-internship.git
cd flyrank-ml-internship && pip install -r requirements.txt
python scripts/run_all.py

The pipeline is deterministic (random_state=42 throughout) and produces outputs/model_results.json, outputs/refresh_queue.csv, and outputs/model_report.md — the source of every figure above. Notebooks documenting each stage of the work live under work/notebooks/: model selection (w05_model.ipynb), the validation/leakage audit (w06_validation_audit.ipynb), and the action playbook (w07_action_playbook.ipynb).
